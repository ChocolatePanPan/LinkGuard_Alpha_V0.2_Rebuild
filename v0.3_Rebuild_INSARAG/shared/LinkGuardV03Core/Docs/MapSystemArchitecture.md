## 一、核心理念

地圖系統不只是「顯示位置」，而是**「災害指揮作戰平台」**。

根據消防人員訪談，需求強調：
- 「地圖要能直接看懂現場」
- 「不能點很多層」
- 「高壓下要快速判讀」
- 「資訊要分層」
- 「最好像作戰地圖」

因此地圖必須是：
- ✅ 開啟 APP 第一頁
- ✅ 最大頁面
- ✅ 指揮核心
- ✅ 全系統主入口

## 四、ICS 分區系統

支援主區 A/B/C 和子區 D1/D2/D3 的多層級分區管理。

**關鍵特性**：
- 主區 A/B/C 支援 3 個子區
- 每個分區可獨立指派搜救隊負責
- 每個分區有獨立的搜救狀態管理
- 顏色編碼快速辨識

**實現位置**: `ICSMapArea` 列舉 (`MapSystemTypes.swift`)

---

## 五、搜救狀態圖層

6 種狀態圖層支援搜救進度管理：

| 狀態 | 顏色 | 含義 |
|-----|------|-----|
| 未確認 | ⚪ 灰色 | 區域待檢查 |
| 搜救中 | 🟡 黃色 | 正在搜索 |
| 已淨空 | 🟢 綠色 | 已完成搜索 |
| 高危險 | 🔴 紅色 | 危險程度高 |
| 禁止進入 | ⬛ 黑色 | 結構崩塌等 |
| 二次搜索 | 🔵 藍色 | 需要重新搜索 |

**實現位置**: `SearchState` 列舉 (`MapSystemTypes.swift`)

## 八、離線地圖（超重要）

**必要性**：災後極可能面臨：
- 沒基地台
- 沒網路
- 沒 WiFi

因此離線能力是**必要功能，不是附加功能**。

**必須功能**：

| 功能 | 說明 |
|-----|------|
| 離線地圖 | 預下載 MBTiles |
| 本地資料庫 | SQLite 儲存 |
| 離線 GPS | 持續定位 |
| 離線標記 | 本地儲存標記 |
| 延遲同步 | 恢復後自動上傳 |
| LoRa 同步 | 備援傳輸 (MQTT) |

**實現位置**: `OfflineMapCache` 結構 (`MapSystemTypes.swift`)

## 十一、設計原則（可靠性）

高壓下最怕：點錯、當機、太複雜

**必要功能**：

| 功能 | 原因 |
|-----|------|
| 大按鈕 | 戴手套操作 |
| 少層級 | 快速操作 |
| 常用固定 | 減少搜尋 |
| 自動儲存 | 防止遺失 |
| 一鍵 SOS | 緊急救命 |
| 色彩統一 | 直覺判讀 |
| 離線優先 | 災後可靠 |
| 地圖快取 | 加速載入 |
| 黑夜模式 | 夜間搜救 |
| 語音操作 | 雙手忙碌 |

---

## 十二、推薦技術棧

| 模組 | 建議 | 理由 |
|-----|------|------|
| 地圖引擎 | Mapbox | 專業 GIS，支援離線 |
| 離線地圖 | MBTiles | 標準格式，高效率 |
| GPS | CoreLocation | 原生支援，可靠 |
| 即時同步 | WebSocket | 低延遲，雙向通訊 |
| 離線資料庫 | SQLite | 輕量，高效 |
| LoRa 同步 | MQTT | 標準 IoT 協議 |
| AI 分析 | 本地 AI + 雲端 | 離線優先 + 雲端備援 |
| 照片定位 | EXIF GPS | 自動座標提取 |

---

## 十三、頁面層級

根據消防人員訪談：

```
1. 地圖          ← 最優先
2. 人員總覽
3. 資源管理
4. 通訊
```

因此：
- **地圖是主頁面** (不是附屬功能)
- 地圖占據最大可用空間
- 其他功能通過懸浮按鈕/快速操作訪問
